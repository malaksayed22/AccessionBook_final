# File storage

Uploaded evidence (lab reports, shipping documents, measurement exports) is stored behind the
`BlobStorage` interface in `src/server/storage.ts`. This page is the operational contract between
the application and the infrastructure phase (P6).

## Drivers

| `STORAGE_DRIVER` | Use                    | Configuration                                        |
| ---------------- | ---------------------- | ---------------------------------------------------- |
| `disk` (default) | development and tests  | `STORAGE_DIR` (default `.local/uploads`)             |
| `s3`             | staging and production | `S3_BUCKET` (required), `S3_REGION`, `S3_KMS_KEY_ID` |

The S3 driver creates its client lazily with `new S3Client({ region })` and the **default
credential provider chain**. There are no access keys in code or environment: in AWS the task role
supplies credentials. `S3_KMS_KEY_ID` selects SSE-KMS; when it is empty, objects use SSE-S3.

## Application guarantees

- **Write-once.** `put` never overwrites. Disk uses the `wx` flag; S3 sends `If-None-Match: *`.
  An existing key raises `StorageKeyExistsError`. Corrections are new objects; documents are voided
  in the database, never deleted from storage.
- **Integrity.** Every S3 upload requests a SHA-256 checksum, verified by S3 on receipt. The
  application also records its own SHA-256 of each file.
- **Encryption on write.** Each `PutObject` states its server-side encryption (`aws:kms` with the
  configured key, otherwise `AES256`).
- **Key validation.** Both drivers reject empty keys, keys over 512 characters, leading slashes,
  backslashes, control characters and `.`, `..` or empty path segments.
- **No delete.** The interface has no delete operation, and the application role needs none.

## Key layout

```
units/<unitId>/<uuid>.<ext>
```

Keys are generated by the server (never from user input); the extension comes from the validated
content type. The `units/` prefix is the only prefix the application role may touch.

## Why files are never public

Files are regulated evidence attached to specific units and experiments. Access depends on who the
user is and which experiment the unit belongs to, which only the application can decide. So every
download goes through an authenticated route that authorises first, then streams bytes from
storage. There are no public URLs, no public-read ACLs and no pre-signed links handed to browsers.

## Bucket requirements (infrastructure phase)

The bucket must be created with all of the following. The application assumes them and does not
check them.

1. **Block Public Access**: all four settings on, at bucket and account level. Object ownership
   "Bucket owner enforced" (ACLs disabled).
2. **Versioning enabled**, so an overwrite or malicious write can always be undone.
3. **Default encryption SSE-KMS** with a customer-managed key (the key `S3_KMS_KEY_ID` names), with
   bucket keys enabled. The key policy allows the task role `kms:GenerateDataKey` and `kms:Decrypt`
   only.
4. **Bucket policy denying non-TLS requests**: `Deny` on `s3:*` for all principals when
   `aws:SecureTransport` is `false`. Consider also denying `PutObject` without
   `s3:x-amz-server-side-encryption` set to `aws:kms`.
5. **Access only through the task role.** The role grants `s3:PutObject` and `s3:GetObject` on
   `arn:aws:s3:::<bucket>/units/*`, plus `s3:ListBucket` on the bucket restricted to the `units/*`
   prefix (see the note below). It has no `s3:DeleteObject`, no `s3:DeleteObjectVersion` and no
   `s3:PutObjectAcl`. No other principal has data access; humans use audited break-glass roles.
6. **Lifecycle rules.** Never expire current or noncurrent evidence versions. Do add a rule that
   aborts incomplete multipart uploads after 7 days. Transition to infrequent-access classes is
   optional; expiration is not allowed.
7. **Access logging.** Server access logs (or CloudTrail S3 data events for the bucket) delivered
   to a separate, write-restricted logging bucket with its own retention.
8. Optional hardening: Object Lock in governance or compliance mode if the retention regime
   requires WORM storage.

### Note on `ListBucket`

`GetObject` on a missing key returns `NoSuchKey` (404) only if the caller has `s3:ListBucket`;
otherwise S3 returns `AccessDenied` (403) to avoid revealing which keys exist. The driver maps
`NoSuchKey`/404 to `null` and rethrows everything else, so the role must hold `s3:ListBucket`
(restricted with an `s3:prefix` condition to `units/*`). Without it a missing object surfaces as a
server error instead of "file not found".
